# 1. 第 2.1.4 节：Nsight Systems Profiler

## 1.1 原文详细翻译

### 为什么需要 profiler

端到端 benchmark 只能告诉我们一次 forward、backward 或 optimizer step 总共花了多长时间，却不能告诉我们时间和内存具体花在了哪里。因此，端到端计时无法直接暴露具体的优化机会。

如果想知道程序在每个组件或函数中花费了多少时间，可以使用 profiler。Profiler 会对程序进行 instrumentation，也就是在函数开始和结束的位置插入记录点，从而收集函数级别的详细执行信息，例如：

- 某个函数被调用了多少次；
- 每次调用平均耗时多少；
- 所有调用累计耗时多少；
- 函数之间具有怎样的调用关系。

普通 Python profiler，例如 `cProfile`，无法正确分析 CUDA kernel 的实际运行时间，因为 CUDA kernel 是在 GPU 上异步执行的。幸运的是，NVIDIA 提供了 Nsight Systems，可以通过命令行工具 `nsys` 分析 CPU 与 GPU 的执行过程。

课程建议使用包管理器或 NVIDIA 官方安装程序安装较新的 Nsight Systems 版本。

### 最基本的 Nsight Systems 用法

使用 `nsys` 非常直接：只需在之前的 Python benchmark 命令前加上 `nsys profile --`。

例如，分析 `benchmark.py`：

```bash
uv run nsys profile -- python benchmark.py
```

命令运行后会生成 Nsight Systems report。可以将 report 下载到本地，在 NVIDIA Nsight Systems 桌面应用中打开。

在图形界面中，如果选中 CPU 一侧 `CUDA API` 行中的某个 CUDA API call，Nsight Systems 会高亮显示 GPU 一侧 `CUDA HW` 行中与之对应的 kernel execution。这样可以把 Python/PyTorch 发起的 CUDA 调用与 GPU 真正执行的 kernel 联系起来。

### 更完整的 profiling 命令

作业给出的较完整命令为：

```bash
uv run nsys profile \
  --trace=cuda,cudnn,cublas,osrt,nvtx \
  --pytorch=functions-trace,autograd-shapes-nvtx \
  --cudabacktrace=all \
  --python-backtrace=cuda \
  --gpu-metrics-devices=0 \
  -- python benchmark.py
```

各参数的含义如下。

#### `--trace=cuda,cudnn,cublas,osrt,nvtx`

指定需要追踪的 API 或事件来源：

- `cuda`：CUDA runtime 和 driver API；
- `cudnn`：cuDNN 深度学习算子；
- `cublas`：cuBLAS 矩阵乘法等线性代数调用；
- `osrt`：操作系统 runtime 事件，例如线程休眠、锁和系统调用；
- `nvtx`：用户或框架添加的 NVTX 标记区间。

#### `--pytorch=functions-trace,autograd-shapes-nvtx`

让 profiler 添加 PyTorch 函数和 autograd 相关信息。`autograd-shapes-nvtx` 还能把 tensor shape 等信息编码到 NVTX annotation 中，从而帮助判断某个 operation 对应哪个模型配置或 tensor shape。

#### `--cudabacktrace=all`

收集 CUDA API call 的 native backtrace，以便从底层调用追溯到触发该操作的位置。

#### `--python-backtrace=cuda`

收集触发 CUDA 调用的 Python stack trace，从而将某个 GPU kernel 对应回 Python 源代码。

#### `--gpu-metrics-devices=0`

采集 GPU 0 的硬件指标，例如利用率、频率或其他可用的 GPU metric。

Profiling 本身不是免费的。Profiler 会记录大量事件、stack trace 和硬件指标，因此会使程序比正常运行更慢。实际使用时应只启用当前分析确实需要的功能。

特别是：

- `--cudabacktrace=all`；
- `--python-backtrace=cuda`；

通常会带来较大的 overhead。如果当前不需要 traceback，应该去掉它们，从而减小 profiling 对运行过程的扰动。

### 使用 NVTX 标记代码区间

课程鼓励尝试不同的 `nsys profile` 命令行选项，并建议使用 NVTX range 标记代码中的逻辑阶段。

NVTX range 会在 Nsight Systems 的 NVTX timeline 中显示成一个带名字的区间。区间中包含的 CUDA API call 和 GPU kernel 可以被归入相应的逻辑阶段。

对于 benchmark，NVTX 可以用于：

- 排除 warm-up；
- 单独标记正式 measurement；
- 区分 forward、backward 和 optimizer step；
- 区分 self-attention 内部的不同阶段。

作业特别建议使用 NVTX range 标记正式测量区间，并配合 `--nvtx-capture` filter，让 Nsight Systems 只抓取正式 measurement，而不记录 warm-up。

### 给 attention 添加细粒度 NVTX 标记

作业给出的示意代码如下：

```python
import torch.cuda.nvtx as nvtx


@nvtx.range("scaled dot product attention")
def annotated_scaled_dot_product_attention(
    ...  # Q、K、V、mask
):
    ...

    with nvtx.range("computing attention scores"):
        ...  # 计算 Q 和 K 之间的 attention scores

    with nvtx.range("computing softmax"):
        ...  # 计算 softmax

    with nvtx.range("final matmul"):
        ...  # attention probabilities 与 V 相乘

    return ...
```

这样就可以在 timeline 上分别看到：

```text
scaled dot product attention
├── computing attention scores
├── computing softmax
└── final matmul
```

随后可以在 benchmark 中把原来的 attention 函数替换为带标记的版本：

```python
cs336_basics.model.scaled_dot_product_attention = (
    annotated_scaled_dot_product_attention
)
```

这种 monkey patch 方式不需要修改原模型结构，就能在 profiling run 中临时替换 operation。

### `torch.compile` 对 profiling 的影响

`torch.compile` 可能把多个 PyTorch operation 融合为较少的 compiled kernels。这样虽然可能提高性能，却会使源代码中的函数与 GPU kernel 不再一一对应，导致 profiler 中难以把时间准确归因到某个 Python operation。

为了正确分析不同组件，可能需要反复调整：

- 哪些函数使用 `torch.compile`；
- 哪些函数不编译；
- NVTX annotation 放在哪一层；
- 是否需要对某些局部 operation 单独编译或取消编译。

目标是在不严重改变程序行为的前提下，让 timeline 中的事件仍能对应回有意义的模型组件。

# 2. Nsight Systems 相关知识扩充

## 2.1 Nsight Systems 和 Nsight Compute 的区别

### Nsight Systems

Nsight Systems 主要回答系统级问题：

- CPU 与 GPU 是否并行工作；
- GPU 是否存在 idle gap；
- 某个 Python/PyTorch 阶段触发了哪些 CUDA kernel；
- kernel launch 是否过于碎片化；
- 数据传输、计算和通信是否重叠；
- forward、backward、optimizer 各自占多长时间。

它适合先从全局找到瓶颈。

### Nsight Compute

Nsight Compute 更关注单个 CUDA kernel 的微观硬件表现，例如：

- achieved occupancy；
- Tensor Core utilization；
- DRAM throughput；
- cache hit rate；
- instruction mix；
- warp stall 原因。

通常的工作顺序是：

```text
端到端 benchmark
-> Nsight Systems 找到最重要的 kernel
-> Nsight Compute 深入分析该 kernel
```

## 2.2 CPU API time 与 GPU kernel time

Profiler 中常同时出现：

- CPU 上的 CUDA API call；
- GPU 上真正执行的 kernel。

由于 CUDA 是异步的，CPU API call 的持续时间通常不等于 GPU kernel runtime。例如，CPU 调用一个 matmul 可能很快返回，但 GPU 随后执行几百微秒。

还要区分：

- kernel launch time；
- queue 中等待的时间；
- GPU execution time；
- CPU 因同步而阻塞的时间。

## 2.3 Latency、self time 与 cumulative time

- 单次 latency：某次调用持续多久；
- self time：不含子调用的自身时间；
- cumulative time：某函数或 kernel 所有调用的总时间；
- count：调用次数。

优化时通常先关注 cumulative time 最大的项目，因为优化一个占总时间 1% 的 operation，即使快 10 倍，对端到端时间的影响仍然很小。

## 2.4 Amdahl 定律

若程序中比例为 $p$ 的部分被加速 $s$ 倍，整体加速比最多为：

$$
S=\frac{1}{(1-p)+\frac{p}{s}}
$$

例如某个 operation 只占总时间的 10%，即使把它完全消除，整体加速也不超过：

$$
\frac{1}{1-0.1}\approx1.11
$$

Profiler 的价值正是帮助确定 $p$，避免优化对端到端性能影响很小的部分。

## 2.5 NVTX 的正确使用方式

推荐使用嵌套、语义明确的 range：

```text
measurement
├── forward
│   ├── transformer_block_0
│   │   ├── attention
│   │   └── ffn
│   └── ...
├── loss
├── backward
└── optimizer
```

NVTX range 不应细到每个极小 Python expression，否则 annotation 本身会产生噪声。应优先标记能够回答实验问题的逻辑边界。

## 2.6 Profiling overhead

Profiler 会改变被测程序，这称为 observer effect。采集越详细，overhead 越大。因此：

- benchmark run 用于获得可信的原始速度；
- profiling run 用于理解时间分布；
- 不应直接把启用了重型 stack trace 的 profiler latency 当作未插桩程序的最终性能。

## 2.7 Kernel name 为什么很难读

cuBLAS、cuDNN、Inductor 和 Triton 生成的 kernel name 可能非常长，并包含 tile shape、datatype、layout 和算法信息。不要只凭名字猜测来源，应结合：

- NVTX range；
- CPU stack trace；
- tensor shape；
- kernel 前后的相邻 operation；
- `CUDA GPU Kernel Summary` 的调用次数。

## 2.8 FLOPs 与 runtime 不成正比

矩阵乘法通常具有较高算术强度：

$$
I=\frac{\text{FLOPs}}{\text{memory bytes transferred}}
$$

它能够反复复用已经载入片上存储的数据，因此可能接近 Tensor Core 的计算吞吐量。

Softmax、norm 和许多逐元素 operation 的 FLOPs 很少，但每个元素都要从 HBM 读取并写回，算术强度较低，常受显存带宽限制。因此：

```text
FLOPs 占比小
```

不必然意味着：

```text
runtime 占比同样小
```

# 3. 第 2.1.5 节：Mixed Precision

## 3.1 原文详细翻译

到目前为止，作业一直使用 FP32：模型参数和 activation 都采用 `torch.float32`。

现代 NVIDIA GPU 包含专门加速低精度矩阵乘法的 Tensor Cores。例如，作业以 NVIDIA B200 的规格为例：其 FP32 峰值吞吐量约为 80 TFLOPS，而 FP16 或 BF16 的峰值吞吐量可以达到约 2500 TFLOPS。因此，使用低精度 datatype 有望显著加速训练和 inference。

但是，直接把整个模型转换为低精度可能降低模型数值准确性和训练稳定性。

例如，实际训练中的一些 gradient 非常小，小到无法由 FP16 表示。如果直接用 FP16 训练，这些值可能下溢并变成 0。

为缓解 FP16 gradient underflow，训练中常使用 loss scaling：先把 loss 乘以一个 scale factor，使 gradient 也按相同比例放大，从而避免过小的 gradient 被舍入为 0。在 optimizer update 前，再把 gradient 除回原来的尺度。

此外，FP16 的动态范围比 FP32 小，较大的数可能溢出为 `inf`，并进一步产生 `NaN` loss。

完整 BF16 训练通常比完整 FP16 训练稳定，因为 BF16 与 FP32 具有相同数量的 exponent bits，因此动态范围接近 FP32。不过，BF16 的有效精度仍低于 FP32，所以它仍可能影响最终模型质量。

为了同时获得低精度计算的速度与 FP32 的数值稳定性，实践中通常采用 mixed-precision training。

PyTorch 通过 `torch.autocast` context manager 提供自动混合精度。Autocast 会根据 operation 类型决定其计算 dtype：

- 某些适合低精度且能从 Tensor Cores 获益的 operation，例如矩阵乘法，会转换到指定低精度；
- 某些需要更大动态范围或更稳定累加的 operation，例如部分 reduction，会保留或提升到 FP32。

示例：

```python
model: torch.nn.Module = ...
dtype: torch.dtype = torch.bfloat16
x: torch.Tensor = ...

with torch.autocast(device_type="cuda", dtype=dtype):
    y = model(x)
```

一个重要原则是：即使被累加的 tensor 是低精度，累加本身也通常应该在更高精度中完成。下一道实验通过反复累加 `0.01`，帮助建立这种直觉。

## 3.2 `mixed_precision_accumulation` 题目详细翻译

运行以下代码并评论结果的准确性：

```python
s = torch.tensor(0, dtype=torch.float32)
for i in range(1000):
    s += torch.tensor(0.01, dtype=torch.float32)
print(s)

s = torch.tensor(0, dtype=torch.float16)
for i in range(1000):
    s += torch.tensor(0.01, dtype=torch.float16)
print(s)

s = torch.tensor(0, dtype=torch.float32)
for i in range(1000):
    s += torch.tensor(0.01, dtype=torch.float16)
print(s)

s = torch.tensor(0, dtype=torch.float32)
for i in range(1000):
    x = torch.tensor(0.01, dtype=torch.float16)
    s += x.type(torch.float32)
print(s)
```

交付物：2–3 句话。

### 这四段代码分别测试什么

#### 实验 1：FP32 输入，FP32 accumulator

```text
FP32 value -> FP32 accumulation
```

理论结果为 10。由于 `0.01` 本身无法被二进制浮点数精确表示，结果仍可能与 10 有很小误差，但 FP32 的有效精度较高，误差通常很小。

#### 实验 2：FP16 输入，FP16 accumulator

```text
FP16 value -> FP16 accumulation
```

误差通常明显更大。每次 addition 的结果都要舍入回 FP16，1000 次舍入误差会逐步累积。当 accumulator 变大时，其相邻可表示数之间的间隔也变大，`0.01` 相对于 accumulator 的有效影响越来越难精确保留。

#### 实验 3：FP16 value 直接加到 FP32 accumulator

```text
FP16 value -> type promotion -> FP32 accumulation
```

虽然 accumulator 是 FP32，但每个 `0.01` 在创建为 FP16 时已经发生量化。将它提升到 FP32 不能恢复丢失的精度。好处是后续 1000 次 addition 在 FP32 中累加，不会继续产生严重的 FP16 accumulator rounding。

#### 实验 4：显式把 FP16 value 转成 FP32 再累加

它与实验 3 的数学信息基本相同：value 在 FP16 创建时已经量化，再转换到 FP32 并不能恢复原始的精确 `0.01`。实验强调的重点是 accumulator dtype，而不是单纯在最后改变输出 dtype。

## 3.3 `benchmarking_mixed_precision` 题目详细翻译

### Part (a)：ToyModel 中各组件的 dtype

考虑：

```python
class ToyModel(nn.Module):
    def __init__(self, in_features: int, out_features: int):
        super().__init__()
        self.fc1 = nn.Linear(in_features, 10, bias=False)
        self.ln = nn.LayerNorm(10)
        self.fc2 = nn.Linear(10, out_features, bias=False)
        self.relu = nn.ReLU()

    def forward(self, x):
        x = self.relu(self.fc1(x))
        x = self.ln(x)
        x = self.fc2(x)
        return x
```

假设模型在 GPU 上训练，参数原本为 FP32，并启用 FP16 autocast。题目要求判断：

- autocast context 中模型参数的 dtype；
- 第一个 feed-forward layer `fc1` 输出的 dtype；
- LayerNorm 输出的 dtype；
- 模型预测 logits 的 dtype；
- loss 的 dtype；
- 模型 gradients 的 dtype。

交付物：列出每个组件的 dtype。

这道题需要实际运行或根据当前 PyTorch autocast policy 验证，不能把“进入 autocast 后所有 tensor 都变成 FP16”当作答案。Autocast 不会永久修改 parameter storage dtype，而是在 operation 执行时为不同算子选择合适的计算 dtype。

在题目描述的典型 CUDA FP16 autocast 行为中，通常应观察到：

| 组件 | 典型 dtype | 原因 |
| --- | --- | --- |
| model parameters | FP32 | autocast 不会原地改写参数 storage |
| `fc1` output | FP16 | Linear 适合低精度 Tensor Core 计算 |
| LayerNorm output | FP32 | normalization/reduction 需要更稳定的计算 |
| logits | FP16 | `fc2` Linear 通常进入低精度计算 |
| loss | FP32 | cross-entropy/reduction 通常使用 FP32 |
| parameter gradients | FP32 | gradient 最终累积到 FP32 parameters 的 `.grad` |

具体行为可能随 PyTorch 版本、device 和 operation 政策变化，所以正式 writeup 应以作业环境中的实测结果为准。

### Part (b)：为什么 LayerNorm 对低精度敏感

问题：

- LayerNorm 的哪些步骤对混合精度敏感？
- 如果使用 BF16 而不是 FP16，是否仍需要特殊处理 LayerNorm？为什么？

交付物：2–3 句话。

LayerNorm 包含 mean、variance、平方、求和、减法和 reciprocal square root。Reduction 会累积许多元素，低精度累加误差可能不断放大；计算方差时还要处理接近数之间的差和平方，容易发生 cancellation、underflow 或 overflow。

BF16 的 exponent 与 FP32 一样宽，因此比 FP16 更不容易 overflow/underflow，但它的 mantissa 更短，舍入误差仍然更大。所以 BF16 显著缓解动态范围问题，却没有消除 reduction accuracy 问题；实际实现通常仍让 normalization 的统计量和累加使用 FP32。

### Part (c)：在 benchmark 中加入 BF16 mixed precision

扩展 benchmark 脚本，使模型能够选择使用 BF16 autocast。然后对 Table 1 中的每种 language model size，比较：

- full FP32；
- BF16 mixed precision；
- forward latency；
- backward latency；
- 随模型规模变化的性能趋势。

题目提示可以使用 `nullcontext`，让开启和关闭 autocast 的代码结构保持一致：

```python
from contextlib import nullcontext

ctx = (
    torch.autocast(device_type="cuda", dtype=torch.bfloat16)
    if use_mixed_precision
    else nullcontext()
)

with ctx:
    logits = model(inputs)
```

交付物：2–3 句话，包含 timing 和趋势评论。

这里要求的是 autocast mixed precision，不是直接调用：

```python
model.to(torch.bfloat16)
```

后者会改变参数的 storage dtype，属于全模型低精度，不具有 autocast 按 operation 选择 dtype 的语义。

# 4. 混合精度相关知识扩充

## 4.1 浮点数的组成

一个二进制浮点数通常由三部分组成：

- sign bit；
- exponent bits；
- fraction/mantissa bits。

Exponent 决定动态范围，mantissa 决定有效精度。

| dtype | sign | exponent | fraction | 总位数 |
| --- | ---: | ---: | ---: | ---: |
| FP32 | 1 | 8 | 23 | 32 |
| FP16 | 1 | 5 | 10 | 16 |
| BF16 | 1 | 8 | 7 | 16 |

因此：

- FP16 比 BF16 有更多 mantissa bits，局部精度更好；
- BF16 与 FP32 有相同数量的 exponent bits，动态范围大得多；
- BF16 比 FP16 更不容易发生 overflow 和 underflow；
- BF16 的舍入误差通常比 FP16 更大。

## 4.2 Dynamic range 与 precision

这两个概念不能混为一谈：

- dynamic range：能够表示的最小与最大数量级；
- precision：相邻可表示数字之间有多密。

BF16 解决了很多 FP16 动态范围问题，但不会让低精度 accumulation 自动变得与 FP32 一样准确。

## 4.3 为什么累加需要高精度

假设不断计算：

$$
s_{i+1}=\operatorname{round}(s_i+x_i)
$$

每一步都发生 rounding。随着累加次数增加，误差可能积累；当 $s_i$ 很大而 $x_i$ 很小时，$x_i$ 甚至可能小于当前 dtype 在 $s_i$ 附近的最小间隔，导致加法结果完全不变。

因此矩阵乘法常采用：

```text
低精度输入乘法 + FP32 accumulator
```

这也是 Tensor Core 能兼顾速度和一定数值稳定性的关键设计。

## 4.4 FP16 underflow、overflow 和 NaN

### Underflow

非常小的 gradient 可能被舍入成 0：

```text
真实的小 gradient -> FP16 无法表示 -> 0
```

这会导致相应参数失去更新信号。

### Overflow

较大的 activation、loss 或 gradient 可能超过 FP16 最大有限值并变成 `inf`。后续 operation 可能出现：

$$
\frac{\mathrm{inf}}{\mathrm{inf}},
\quad
0\times\mathrm{inf},
\quad
\mathrm{inf}-\mathrm{inf}
$$

并产生 `NaN`。

## 4.5 Loss scaling

设原始 loss 为 $L$，选择 scale $S$：

$$
L'=SL
$$

则 backward 得到：

$$
\nabla_\theta L'=S\nabla_\theta L
$$

放大后的 gradient 更容易落入 FP16 可表示范围。Optimizer update 前再执行 unscale：

$$
\nabla_\theta L=\frac{1}{S}\nabla_\theta L'
$$

### Static loss scaling

始终使用固定 $S$。实现简单，但 scale 太小无法避免 underflow，太大又会导致 overflow。

### Dynamic loss scaling

根据 gradient 是否出现 `inf` 或 `NaN` 自动调整 $S$：

- 若连续若干 step 稳定，则增大 scale；
- 若发现 overflow，则跳过 update 并减小 scale。

FP16 训练通常需要 loss scaling。BF16 具有更大的动态范围，通常不需要 loss scaling，但仍应根据模型与硬件实测。

## 4.6 Autocast 不会做什么

Autocast：

- 不会永久把整个模型参数改成低精度；
- 不会保证所有 operation 都使用相同 dtype；
- 不会自动解决所有数值稳定性问题；
- 不等同于 optimizer state sharding 或 activation checkpointing；
- 不等同于 loss scaling。

它的核心作用是根据 operation policy 自动选择计算 dtype，并插入必要的 cast。

## 4.7 为什么低精度可能更快

低精度带来多方面优势：

1. Tensor Cores 对 FP16/BF16 matmul 吞吐量更高；
2. 每个元素占用更少 bytes，降低 HBM 读写量；
3. 相同显存可容纳更多参数或 activation；
4. cache 和片上 SRAM 可以容纳更多元素；
5. 某些通信场景传输的数据量更小。

但实际 speedup 取决于瓶颈：

- 大型 matmul 更可能获得显著 Tensor Core speedup；
- 小模型可能受 kernel launch 和 Python overhead 影响；
- memory-bound operation 可能主要受 bytes 减半而加速；
- FP32 operation、cast 和非融合 kernel 会限制端到端收益。

## 4.8 为什么模型越大，mixed precision 趋势可能不同

较大模型拥有更大的矩阵乘法，更容易让 Tensor Cores 获得高利用率，因此 mixed precision 的相对收益可能随模型规模增加而更明显。

但较大模型也可能遇到：

- 显存容量限制；
- activation memory；
- optimizer state memory；
- kernel workspace；
- memory bandwidth；
- 不同 shape 的 kernel efficiency。

因此最终趋势必须由实验验证，而不能只从峰值 TFLOPS 推断。

## 4.9 混合精度 benchmark 的公平比较

FP32 与 BF16 autocast 应保持以下条件相同：

- model config；
- batch size；
- context length；
- warm-up steps；
- measurement steps；
- loss definition；
- training mode；
- GPU；
- 是否启用 compile；
- measurement boundary。

还应分别记录：

- latency；
- std；
- peak memory；
- 是否 OOM；
- 是否出现 `inf`/`NaN`；
- 输出或 gradient 与 FP32 reference 的误差。

## 4.10 Mixed precision 与 OOM

Mixed precision 可能降低 activation 和部分临时 tensor 的显存，但不保证所有训练状态都减半。如果 parameters 仍保存为 FP32，optimizer state 也通常保持 FP32，则主要节省来自低精度 activation 和计算副本。

所以不能简单认为：

```text
BF16 mixed precision = 总训练显存减半
```

实际比例取决于参数、activation、gradient、optimizer states 和 workspace 各自占峰值显存的多少。

# 5. 两节内容之间的联系

第 2.1.4 节和第 2.1.5 节共同构成一个完整的性能优化流程：

```text
端到端 benchmark
-> Nsight Systems 定位时间分布
-> 判断主要 operation 与 kernel
-> 使用 mixed precision 改变计算 dtype
-> 再次 benchmark 比较端到端收益
-> 再次 profile 解释收益来自哪里
```

Nsight Systems 可以帮助回答：

- BF16 是否让 matmul kernel 变快；
- kernel 名称或实现是否发生变化；
- matmul 在总时间中的占比是否下降；
- cast kernel 是否引入明显开销；
- softmax、norm、optimizer 等 FP32 或 memory-bound operation 是否成为新的瓶颈。

这体现了系统优化中的基本循环：

```text
测量 -> 定位 -> 优化 -> 验证 -> 再定位
```

# 6. 学完这两节应该掌握什么

## 6.1 Nsight Systems 部分

- 能区分端到端 benchmark 与 profiler；
- 理解 CUDA API call 和 GPU kernel execution 的区别；
- 会用 `nsys profile` 生成 report；
- 会用 NVTX 标记 warm-up、forward、backward 和 optimizer；
- 会在 `CUDA GPU Kernel Summary` 中查看 cumulative time 和 count；
- 能把重要 kernel 对应回模型 operation；
- 理解 profiling overhead；
- 能解释为什么 FLOPs 少的 operation 仍可能占显著 runtime；
- 知道应先优化累计时间占比大的部分。

## 6.2 Mixed precision 部分

- 理解 FP32、FP16、BF16 的 exponent 和 mantissa 差别；
- 区分动态范围与有效精度；
- 理解低精度 accumulation 为什么会积累误差；
- 理解 FP16 underflow、overflow、`inf` 和 `NaN`；
- 理解 loss scaling 的数学原理；
- 知道 BF16 为什么通常比 FP16 稳定；
- 理解 autocast 是按 operation 选择 dtype，而不是把整个模型永久转换；
- 知道 normalization 和 reduction 为什么常需要 FP32；
- 能设计公平的 FP32 与 BF16 benchmark；
- 不把直接创建 BF16 parameters 误认为 autocast mixed precision。

## 6.3 最重要的系统思维

性能优化不能只看峰值硬件指标，也不能只看 FLOPs。必须同时考虑：

- 实际 kernel 时间；
- kernel 调用次数；
- 算术强度；
- 显存带宽；
- 数值精度；
- 峰值显存；
- profiler overhead；
- 端到端 speedup。

最终应以真实 workload 的测量结果为依据，而不是仅凭理论直觉判断优化是否有效。
